# Internal service mTLS gate — 2026-07-17

## Outcome

The production Agent API service bridges now have an executable authentication
boundary instead of relying on development identity headers.

- `agent-api` creates one TLS 1.3 client from the internal CA, its SPIFFE client
  certificate and private key. Any configured internal service URL must use
  HTTPS; missing or invalid key material stops the production process.
- `build-api`, `runtime-api`, `attachments-api`, `commerce-api` and `kernel-api`
  expose a separate TLS 1.3 internal listener with mandatory verified client
  certificates. Their human/OIDC listener remains separate.
- A client URI must be exactly
  `spiffe://<trust-domain>/service/<allowlisted-service>`, be current and allow
  client authentication. Each downstream service grants its own configured
  scopes after certificate verification.
- A verified service may delegate only `X-Tenant-ID` and optional
  `X-Project-ID`. `X-Principal-ID`, principal kind/role, agent/user identity and
  scopes are rejected on input and are regenerated by the trusted middleware.
- The Agent clients no longer send principal or scope headers. The authenticated
  client certificate is the only authority for the service principal.

An end-to-end test creates an ephemeral CA, server certificate and SPIFFE
client certificate, starts the real internal TLS server, calls it with the real
client transport, verifies the delegated tenant in handler context, and proves
that a client without a certificate cannot connect.

## Runtime contract repair

The Agent rollback contract carries a deployment ID, while the old runtime HTTP
route required an environment ID. An additive deployment-scoped rollback route
now resolves the immutable deployment-to-environment binding inside the runtime
store before applying the rollback. Deploy and rollback also enforce the
optional expected environment revision while preserving idempotent replay.

## Honest remaining boundary

This closes the code-level service authentication and Agent runtime/attachments
bridges. It does not claim a live certificate ceremony or deployed internal
listeners. OpenBao-issued admin service certificates, Kubernetes Secret mounts
and live handshake evidence remain an operations gate. The legacy Agent source
gateway also stays fail-closed: its v1 mutation signatures do not carry the
workspace plan/receipt/attestation context required by Project MCP v2.
